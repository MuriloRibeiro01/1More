## Riscos técnicos registrados
- **R-01 — Ordem do `server_version` no pull** (levantado pelo Dumont, 2026-10-14). A `server_version_seq` é atribuída no INSERT/UPDATE, não no commit. Uma transação que pega a versão N e comita depois de outra com N+1 fica invisível para o cliente que já puxou até N+1, e a alteração se perde no pull.
  → Obrigatório no T-003: teste de aceite concorrente (duas transações intercaladas) e uma solução escolhida pelo Tesla. Opções: atribuir a versão com lock/serialização no push, ou limitar o pull ao "high-water mark" seguro (versões abaixo da menor transação ainda aberta). Revisar com o Sérgio e registrar em ADR.
- **R-02 — Spring Boot 3.5 sem suporte OSS** (levantado pelo Leônidas, 2026-10-14; severidade média). O suporte OSS do Boot 3.5 acabou em 30/06/2026 e a 3.5.16 (`backend/pom.xml:9`) é a última release OSS. Nenhum patch de segurança novo chega a Spring Security/Framework/Tomcat nessa linha. O CLAUDE.md fixa "Spring Boot 3".
  → **Decidido (Atlas, 2026-10-14):** migrar para Boot 4.0.x na T-001b, antes do T-002; o usuário pode rever. O merge da T-001 segue na 3.5.16. Ver ADR-002.
- **R-03 — Segurança para o T-002** (Leônidas). (a) A app não pode subir com `JWT_SECRET` ausente, com menos de 32 bytes ou igual ao placeholder do `.env.example`. (b) Login nunca autentica conta com `deleted_at` preenchido. (c) Recadastro de e-mail de conta em tombstone (30 dias) só depois de verificar o e-mail. Cada item com teste de aceite escrito antes (TDD).
- **R-04 — Autorização no sync, T-003** (Leônidas; crítico se faltar). `user_id` sempre vem do token e nunca do payload, e toda query filtra por `user_id`. Push com id de outro usuário é rejeitado sem sobrescrever. Push do `app_user` aceita só uma whitelist (`nome`, `unidade`, `meta_dias_semana`, `fuso`), nunca `email`/`consentimentos`/`deleted_at`. Testes de aceite: usuário B não lê (pull) nem sobrescreve (push) dados de A, inclusive com `client_op_id` igual.
- **R-05 — Histórico de consentimento LGPD** (Leônidas; média, tarefa de LGPD). `app_user.consentimentos` (jsonb) guarda só o estado atual. Para o ônus da prova (LGPD art. 8º §2º) e para as revogações, criar uma tabela append-only de eventos de consentimento (finalidade, concedido/revogado, versão do termo, timestamp). Em produção: banco com TLS (`sslmode=verify-full`) e segredos vindos de secret manager.
- **R-06 — Tombstone de `user_settings` não libera um novo registro** (Dumont/Tesla, 2026-10-14; baixa, T-003). `ux_user_settings_user` (V1) é único mesmo com `deleted_at`: depois de uma exclusão lógica, o push de um settings com **novo id** para o mesmo usuário viola a constraint. → No T-003 o push de `user_settings` faz upsert por `user_id` (reativa e atualiza o registro existente, mantendo o id do servidor) ou rejeita de forma explícita, com teste de aceite. O teste `tombstoneDeUserSettingsNaoLiberaSegundoRegistroDoMesmoUsuario` documenta o comportamento atual.
- **R-07 — Porta do Postgres de dev** (Tesla, 2026-10-14; informativo). O compose publica em `127.0.0.1:${POSTGRES_PORT:-5433}` por causa de um PostgreSQL nativo na 5432 desta máquina. O CLAUDE.md já foi atualizado para a 5433. **Fechado (Atlas, 2026-10-14).**
- **R-09 — `app_user` fora do padrão de tabela sincronizável** (Sócrates, 2026-10-14; informativo, T-003). `app_user` não tem `user_id` nem o índice `(user_id, server_version)` (o próprio `id` é o usuário). → No contrato do T-003, definir como o pull entrega o perfil (filtro por `id` = usuário do token) e cobrir com teste de aceite. A autorização segue a R-04.
- **R-08 — `server_version` por linha × resposta do push** (Sérgio, 2026-10-14; baixa, T-003). (a) O trigger `set_server_version` (V1:17-24) gera versão nova em **todo** UPDATE, inclusive quando nada muda. Assim, um push que reaplica dados idênticos ou um job técnico (ex.: `last_login` na T-002) faz o registro voltar no pull de todos os dispositivos. → No T-003 o push só grava a linha se houver diferença (ou o trigger ganha `WHEN (OLD.* IS DISTINCT FROM NEW.*)` numa migração nova), com teste de aceite. (b) Cada linha de um lote recebe o próprio `nextval`, mas `sync_push_log` guarda uma única `server_version` por `client_op_id`. → Definir no contrato do T-003 qual valor é devolvido (a maior versão do lote) e testar que um reenvio devolve exatamente o mesmo valor.
- **R-10 — Segurança mobile para o T-002 em diante** (Leônidas, 2026-10-15). (a) O scheme `onemore://` pode ser registrado por qualquer app: nunca transportar token ou código de login por ele. Se houver login externo ou link de redefinição de senha, usar PKCE e App Links/Universal Links verificados (https), com teste de aceite. (b) Tokens só no `expo-secure-store`, nunca no LocalStorage do WatermelonDB nem em log. (c) Remover `console.*` do bundle de release (ex.: `babel-plugin-transform-remove-console`) antes de existir dado pessoal. (d) Quando entrarem dados de saúde (RN-25), avaliar criptografia do SQLite local (SQLCipher) e reavaliar o `allowBackup`. (e) O plugin `@lovesworking/watermelondb-expo-plugin-sdk-52-plus` é pequeno (~150 linhas) e pouco mantido: copiar para `mobile/plugins/` como plugin local na próxima troca de SDK, ou manter fixo na versão exata. (f) `npm audit`: refazer a cada troca de SDK do Expo, nunca com `npm audit fix --force`. O `node-forge` vulnerável passa a importar se o projeto adotar code signing do `expo-updates`.
